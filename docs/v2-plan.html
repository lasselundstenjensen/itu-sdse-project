Lecturer tooling — plan overview

Grading harness for the v2 exam extension: students deploy their trained model to Digital Ocean and monitor it for drift. We probe, score, and display.

FastAPI wraps the interface for both SPAs; the event engine imports it in-process. §01 · Components

What we are building

— four pieces, one interface underneath.
01

Event engine — probe & stress

Scheduled worker. Sends a health inference request every few minutes to each ready-for-events endpoint. Records reachability and correctness as two independent indicators per probe. Periodically injects drift-inducing traffic to test that students' retrain-and-redeploy loop actually fires.

SERVICESCHEDULED
02

Leaderboard dashboard — public SPA

Read-only, viewable by everyone. Claude-Status-style horizontal bars per model over the last N probes, plus aggregate uptime %, correctness %, last-seen timestamp, and successful-recovery count. Team members sign in only to mutate their own row.

SPAREAD-ALL
03

Admin SPA — team management

Lecturer-only. Assign, enable, and disable teams and their credentials. Force-toggle any team's ready_for_events flag when needed. Separate SPA from the leaderboard so its auth surface is smaller.

SPALECTURER
04

Access control — read-all, write-own

Everyone can read. Only the owning team can change their endpoint URL and ready_for_events toggle. Team id + password, bcrypt-hashed. Deliberately simple — no OAuth, no SSO.

POLICYbcrypt

§03 · Event engine · detail

Probe worker behaviour

— platform/event-engine/
  • Runs every few minutes. For each model with ready_for_events = true, fires one health inference request to the student's Digital Ocean endpoint.
  • Two independent indicators per probe: reachable (did the endpoint respond?) and correct (was the answer right?). Correctness is null when the endpoint is unreachable.
  • Periodically injects drift-inducing traffic to test that students' monitoring + retrain-and-redeploy loop actually fires and recovers.
  • Detects recovery when a run of correct=false is followed by a return to correct=true — or, more strictly, by a change in the student's advertised model_version via GET /version.
  • Appends every result to the Status DB via the shared repository module — no direct file writes. One interface, two callers.
  • Student endpoint contract: GET /health, POST /infer, GET /version. Schemas in platform/registry/schemas/.
§04 · Data

Registry & Status — two file-based stores

— separated so probe history can grow without bloating the registry.

Registry DB

  • Teams — team_id, password_hash, enabled, created_at
  • Models — model_id, owner_team_id, display_name, endpoint_url, ready_for_events, registered_at, updated_at
  • Written by admin SPA (teams) and by team members via dashboard (their own model rows)
  • Read by both SPAs and the event engine

Status DB

  • Probes — probe_id, model_id, timestamp, reachable, correct, latency_ms, response_snippet, probe_kind
  • Recoveries — model_id, detected_at, redeployed_at, new_model_version
  • Append-only; written by event engine only
  • Read by the dashboard SPA for the leaderboard timelines

Repository interface

  • teams · create, list, get, set_enabled, verify_password, delete
  • models · create, list, get, list_by_team, update_endpoint, set_ready, delete
  • probes · append, list_by_model(since, limit), aggregate
  • recoveries · append, list_by_model

Why separate?

  • Probe history grows fast — keep registry small and hot
  • Rotate / prune status independently of team & model rows
  • Swap backend (JSONL → SQLite → Postgres) without touching consumers
  • Clear write-authority boundary: engine only writes Status; SPAs only write Registry
§05 · Stack & layout

Committed choices

— boring on purpose.

Stack

  • Python everywhere on the backend — matches the course
  • FastAPI wraps the shared repo module → both SPAs
  • Event engine imports the repo module in-process — one interface, two callers
  • SPAs are vanilla HTML + JS, no build step
  • Alpine.js allowed as an optional sprinkle if reactivity gets painful
  • Password hashing via bcrypt (passlib)

  • Fancy auth (OAuth, SSO)
  • Deploying anything to Digital Ocean ourselves — students own their endpoints

Strategic notes

01 · One interface, two callers. The repository module is the only thing that touches the file stores. Both SPAs go through FastAPI; the event engine imports the module directly. Swapping backends later doesn't touch consumers.

02 · Two indicators, not one. Reachability and correctness are recorded independently every probe. A model that responds with wrong answers is a different failure mode than one that doesn't respond at all — and the leaderboard must show both.

03 · Drift is injected on purpose. The event engine is not just a health checker; it is a stressor. The point of the exam extension is that students' retrain-and-redeploy loop fires, and we can only score that if we cause it.

04 · Read-all, write-own. Public read access is the whole point of the leaderboard. Writes are narrow: teams edit their own row, lecturers manage everything. No OAuth, no sessions library — team id + bcrypt password is enough.

05 · Student-facing artifacts are read-only. README.md, notebooks/**, action.yml, and the student-facing bits of .github/workflows/** stay recognisable to students who forked earlier. All v2 tooling lives under platform/.
