Lecturer Tooling
Plan Overview

Grading harness for the v2 exam extension: students deploy their trained model to Digital Ocean and monitor it for drift. We probe, score, and display.

Branch: v2 Stack: Python · FastAPI · vanilla HTML+JS 7 slides ~5 min
Overview · Four tooling components

What we are building

01 · Event engine

Probe & stress

Scheduled worker. Sends a health inference request every few minutes to each "ready-for-events" endpoint. Records reachability + correctness independently. Injects drift to test recovery.

02 · Dashboard

Leaderboard SPA

Public read-only. Claude-Status-style bars per model over the last N probes. Aggregate uptime / correctness %, last-seen, recovery-event count.

03 · Admin SPA

Team management

Lecturer-only. Assign, enable, and disable teams and their credentials. Force-toggle any team's ready-for-events flag when needed.

04 · Access control

Read-all, write-own

Everyone can read. Only the owning team can change their endpoint URL and ready-for-events toggle. Team-id + password, hashed. Deliberately simple.

Component 01 / 04
Event engine
Scheduled probe worker  ·  platform/event-engine/
  • Runs every few minutes. For each "ready-for-events" model, fires one health inference request.
  • Two independent indicators per probe: reachable (did the endpoint respond?) and correct (was the answer right?).
  • Periodically injects drift-inducing traffic to test that students' monitoring + retrain-and-redeploy loop actually fires.
  • Detects recovery when a run of correct=false is followed by a return to correct=true.
  • Appends every result to the Status DB via the shared repository module — no direct file writes.
Data · Two file-based stores

Registry & Status

Registry DB

  • Teams — team_id, password_hash, enabled, created_at
  • Models — model_id, owner_team_id, display_name, endpoint_url, ready_for_events, timestamps
  • Written by admin SPA (teams) and by team members via dashboard (their own model rows)
  • Read by both SPAs and the event engine

Status DB

  • Probes — timestamp, reachable, correct, latency_ms, probe_kind
  • Recoveries — detected_at, redeployed_at, new_model_version
  • Append-only; written by event engine only

Why separate?

  • Probe history grows fast — keep registry small
  • Rotate / prune status independently
  • Swap backends (SQLite → Postgres) without touching consumers
Stack & layout

Committed choices

Stack

  • Python everywhere on the backend — matches the course
  • FastAPI wraps the shared repo module → both SPAs
  • Event engine imports the repo module in-process — one interface, two callers
  • SPAs are vanilla HTML + JS, no build step
  • Alpine.js allowed as an optional sprinkle if reactivity gets painful
  • Password hashing via bcrypt (passlib)
